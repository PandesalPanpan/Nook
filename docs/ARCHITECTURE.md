# Local-first architecture

Normal writes commit the entity, search index and a coalesced durable outbox snapshot in the same database transaction. React and Compose observe the device database. Firebase transport runs outside the capture path. Optional authenticated sessions own active namespaces and remount editors on account changes; local-only mode does not initialize Firebase.

Every record carries a stable UUID, account namespace, schema version, creation/update milliseconds, writer client ID, archive state and deletion tombstone. Do date and deadline are separate task fields. Credentials are intentionally absent from shared settings and records.

V1 deletion tombstones win over every live version of the same record ID, including later-clock edits by disconnected clients. Deletion is permanent; Archive is the reversible operation. Live records compare update time, then lexical client ID. Updates advance beyond the local record's previous timestamp. Tombstones must remain in cloud and local stores; they must not be garbage-collected without a future protocol proving all clients have observed them. Device clock skew remains a limitation of live-record timestamp ordering.

Processing a capture into a task, note, project or resource atomically creates the destination and tombstones the source. A second processing attempt fails. Notes preserve attachment references. The transport must compare versions inside a Firestore transaction and acknowledge only the exact outbox version transmitted, so a concurrent local edit is never lost.

Guest migration moves records and outbox entries atomically into the signed-in account, preserving stable IDs and existing account data. Compound account/record keys prevent identical IDs across accounts from colliding. The database upgrades legacy records into this compound-key table. Sign-out must stop and await the SyncEngine before changing the active namespace; stopped workers discard late results.

SyncEngine pushes due outbox snapshots, conditionally acknowledges the transmitted version and then pulls cloud records. Failed pushes persist capped exponential retry delays. Guest accounts never invoke transport. Both platforms use namespace-scoped Firebase transports with automated emulator gates. Native WorkManager uses account-specific immediate and periodic jobs, connected to session scheduling and cancelled before credential changes.

Web search uses an IndexedDB multi-entry term index and intersects prefix matches. Android uses a Room FTS4 table. Both index changes occur in record transactions and support project, area and before filters. Archive remains searchable. Database migrations backfill indexes and preserve records. FTS queries use implicit intersections, supported by both standard and enhanced SQLite FTS4 syntax ([SQLite reference](https://www.sqlite.org/fts3.html)).

Web attachments store original bytes in a separate account-scoped IndexedDB table. Android Room stores originals in 256 KiB chunks to avoid SQLite CursorWindow limits; migration preserves existing records. Capture metadata and original bytes commit together, and processing reparents attachment metadata. Native photo capture limits originals to 50 MB total per capture.

Both platforms use the same ZIP format: nook.json, Markdown notes/daily notes and original attachment files indexed by stable IDs. Restore validates every record and attachment before an atomic account-bound merge. Repeat restore is idempotent and cannot resurrect a tombstone. The importer rejects unsafe paths and imposes archive/file-count limits. Android uses the system document picker for offline backup export/restore and saving original files. Both sync engines reconcile cloud originals after metadata, with verified bounded downloads, upload callbacks, deletion cleanup, durable retry eligibility and account/cancellation fences.

Explicit owner deletion atomically tombstones owned attachments and linked reminders, removes local originals, updates search and queues the tombstones. Processing reparents attachments before deleting the capture. Receiving a parent tombstone does not infer child deletion, because processing updates can arrive out of order; received attachment tombstones independently clear their original bytes.

Android share capture, launcher shortcuts, widgets and reminder actions use the same account-bound Room repository. Five Glance widgets query only the record kinds they need. Mutations enqueue network-independent system refresh work. Task/deadline and daily Inbox reminders use deferrable WorkManager jobs, with fresh account, deletion and completion checks before delivery. Inbox review skips empty queues when configured. Later schedules another attempt in one hour while retaining the daily review clock. Notification permission is requested only when configuring reminders. Delivery can be delayed by Android battery scheduling.

Task completion is a domain mutation on both platforms. A repeating task keeps its completed occurrence and atomically creates one next task with a durable outbox entry. Daily/weekly intervals follow the anchor; monthly intervals clamp short months and return to the original day afterward. Do date and deadline advance together, preserving their distance. Configured reminders advance by local calendar days, preserving the notification's local time through daylight-saving changes, and a project's explicit next action follows the new occurrence. Recurrence never runs on ordinary reads or capture.

Occurrence IDs use SHA-256 of the same recurrence ID and scheduled date on Android and web. Completing the same occurrence on two clients therefore merges into one next task when the cadence is unchanged. Repeated completion and undo/recompletion cannot duplicate or resurrect an already deleted occurrence. Completion does not skip overdue scheduled instances; users can reschedule the active task explicitly. Disabling recurrence removes the association from the active occurrence without altering completion history. Separate reminder/repeat controls preserve unsaved task edits.

Notes store portable Markdown. Both editors format the selected text or selected lines and provide headings, bold, italic, lists, checklists, quote, code and links. Web renders with react-markdown/GFM; native Compose uses a styled Markwon TextView for preview. No remote-image loader or HTML execution is enabled. External links open only on explicit interaction; native accepts HTTP, HTTPS and mailto schemes.

Wiki links resolve by stable note ID or an unambiguous case-insensitive title, with optional display aliases. Link pickers insert stable IDs; typed title links resolve against current titles. Preview and backlinks operate on parsed Markdown text nodes, excluding code examples and existing links. Opening a preview link saves the current draft locally before navigation. Native offers a searchable Link note dialog. Original attachments can be added to an existing record without creating an Inbox capture; owner metadata, note attachment IDs, original bytes and outbox entries commit together. Task/note saves retain attachment and reminder metadata updated by separate controls.

Daily notes are created only when the user opens a day's scratch note. The calendar date becomes immutable metadata; journal text remains portable Markdown. Both platforms use the account-scoped identity `daily-YYYY-MM-DD`, reuse an existing live dated note (including imported notes), and commit creation/index/outbox atomically. Deleted generations stay tombstoned. Explicitly creating another note for a previously deleted date advances the shared numeric generation without resurrecting the old identity. Concurrent offline creation of the same generation merges using the normal conflict policy. Related record IDs support tasks, notes and PARA items without moving them. Daily-note links to ordinary notes participate in backlinks. Calendar agendas distinguish do dates, deadlines, project target dates and local-time reminder schedules.

Weekly review presents Inbox processing, active projects, Areas and next focus. Its device-local draft is scoped to account and Monday-based week, preserving the selected section, focus text and opened record IDs across navigation/recreation. Review drafts are temporary UI state; confirmed focus is a normal searchable/exportable note with a durable outbox. Saving again that week updates one shared `weekly-focus-YYYY-MM-DD` identity; deleted generations remain tombstoned. No record is reorganized or completed by reviewing it. Draft recovery and focus persistence work without Firebase. Web editors refresh pristine drafts from committed records while retaining unsaved user edits when separate controls or incoming versions update the record.


Web original-transfer reconciliation uses a local Dexie v7 ledger and indexed original revisions. Every files creation/replacement receives a fresh revision through Dexie hooks; the v6 upgrade preserves bytes and assigns revisions once. Successful operations are acknowledged only if the record and original revision still match after the transport completes. Entries are scoped to account, complete record payload/version, local original revision and Firebase project/bucket. Matching successful entries skip byte reads and Storage requests for 15 minutes; expiry, a backward clock, missing/replaced local bytes, metadata edits or another backend trigger integrity checks again. Failures and cancelled/stale operations never become acknowledgements. Rechecks allow recovery if cloud originals disappear externally. The ledger/revisions are operational local metadata, excluded from ZIP manifests and cloud payloads. Android Room v4 uses the same 15-minute successful-transfer policy. Originals receive a fresh revision in the atomic putOriginal transaction; the v3 migration assigns part-zero revisions without loading blobs. The account-scoped original_transfers table stores backend/version/revision acknowledgements. Revision-only queries avoid reconstructing unchanged originals, and conditional acknowledgement fences concurrent bytes/metadata changes. Room migrations preserve original chunks and user records; operational revisions/acknowledgements remain outside exports and cloud payloads.


File-sync progress is operational local state. Both engines publish an account-fenced snapshot of eligible file checks after the metadata pull: total, checked, failed, current filename and checking/uploading/downloading/removing phase. Counts include cached integrity checks and deletion cleanup. Failed checks retain metadata/originals for retry and do not prevent unrelated files from proceeding. SDK upload callbacks expose actual transferred bytes, capped at twenty progress updates per file; listeners are removed on completion/cancellation and late callbacks are rejected. Downloads use the existing bounded getBytes API and show an indeterminate downloading phase until verified original bytes commit locally. This does not fabricate per-byte download percentages.

Web AccountSession clears file snapshots at account changes/sign-out and preserves final failure counts for safe retry feedback. Native AccountSession does the same for manual attempts. SyncWorker writes bounded progress through a conflated channel: SDK callbacks enqueue snapshots without waiting for WorkManager database writes, and completion drains the last snapshot. Account-specific WorkInfo observation reads only running jobs, chooses the latest immediate/periodic progress and drops finished/cancelled file details. The Sync screen exposes the progress through polite live status text, with long filenames wrapping. Completed background checks retain the existing durable last-check history; file names/progress are not exported to cloud or ZIP manifests. Capture stays independent of this observer/transport path.

Android authentication preserves an app-owned sign-out fence in nook-auth-local preferences, scoped to configured Firebase project/application IDs. SignedOutFence commits a Boolean before FirebaseAuth.signOut can complete; FirebaseAuthPort masks cached identities and clears the SDK user on initialization while the fence is set. Only a successful explicit email registration/sign-in or Google sign-in clears it. Failed or cancelled credential attempts retain the fence. This prevents an immediately stopped/restarted app from restoring a cached signed-out identity, independent of SDK persistence timing. The fence contains no user IDs, credentials or tokens, and is outside Room, outboxes, cloud payloads and backups. Existing installations without a fence continue normal cached-auth restoration. The configured cold-surface emulator gate exercises sign-in restoration, actual system surface entry points and persistent disconnection in separate OS processes.
