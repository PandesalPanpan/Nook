# Firebase setup

Native Auth credential changes now await cancellation of WorkManager jobs tagged `nook-sync` before invoking Firebase. A failed cancellation barrier leaves credentials intact and reconciles the previous account's in-process sync engine. Domain ordering/recovery tests and an actual WorkManager emulator test pass; cancellation leaves unrelated queued jobs intact. The barrier uses [WorkManager's suspending Operation.await](https://developer.android.com/reference/androidx/work/OperationKt), avoiding a blocking Future wait.

Android has an explicit public configuration loader. Copy `apps/android/nook-firebase.example.json` to `apps/android/app/src/main/assets/nook-firebase.json` and provide the dedicated Nook Android app's API key, Firebase application ID, project ID and storage bucket. The actual configuration filename is ignored by Git. Missing configuration returns local-only mode; incomplete fields and demo projects without emulator routing are rejected. Android emulator routing uses `emulatorHost: "10.0.2.2"`. MainActivity and SyncWorker invoke this loader through a serialized process bootstrap. Configured startup restores the Auth session and persists its namespace before rendering; missing configuration skips Firebase. Settings → Sync now exposes email registration/sign-in, Google entry, the actual outbox, manual sync and disconnect.

For native Google sign-in, also set `googleWebClientId` to the dedicated project's **web OAuth client ID**, enable the Google Auth provider and register the Android signing certificate fingerprints. The button uses Credential Manager's explicit Google flow, exchanges its ID token through Firebase, and applies the same safe guest merge as email. A dismissed picker preserves the current sync engine. Disconnect also clears provider credential state. Real Google OAuth remains unverified without a provisioned project. Reference: [Firebase Android Google authentication and Credential Manager](https://firebase.google.com/docs/auth/android/google-signin). Google ID 1.1.1 is the documented adapter version compatible with the project's Kotlin 2.2 compiler; 1.2.1 uses incompatible Kotlin 2.4 metadata. Credential Manager uses stable 1.6.0.

Windows configured native UI gate: `npx firebase emulators:exec --project demo-nook --only auth,firestore,storage "powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-native-auth.ps1"`. It temporarily supplies public demo configuration, verifies actual asset bootstrap and native email controls against Auth/Firestore, restores the prior configuration and network state, then rebuilds the ordinary APK. The passing flow starts through Share to Nook with a stale saved namespace, restores the guest namespace before saving, preserves private records, tests failed sign-in, then registers and uploads without pressing Sync. It also captures/archives offline and verifies automatic catch-up after reconnection, removes posted/deferred reminders on disconnect, signs back in and recreates the activity. Account actions run in the process scope so account-keyed UI remounts cannot interrupt a successful merge. Password fields are transient Compose state and are cleared on submission, outside saved instance state, records and exports.

Native automatic sync observes committed account-scoped Room outbox payloads with a 250 ms debounce; retry counters and acknowledgements do not create retry loops. WorkManager owns network constraints and exponential retry, with one pending successor per account, a 30-second refresh while the process is visible, and a persisted 15-minute background refresh. The background interval is deferrable under Android's battery/network constraints, not an exact timer. Sign-in/out stops and joins the observer and foreground timer before awaiting tagged work cancellation. Failed credential changes resume the previous account's scheduler. Share, widget, project-widget setup, reminder delivery and Later entry points restore cached Auth before selecting a repository; this does not wait for a network request. Namespace publication cancels old reminder jobs and posted notifications, then refreshes widgets/reminders for the new namespace. References: [WorkManager unique work](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/manage-work), [Periodic work constraints](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest), [Process lifecycle](https://developer.android.com/reference/androidx/lifecycle/ProcessLifecycleOwner).

Local-only mode needs no Firebase project. The repository's demo-nook emulator configuration never selects another app's project.

Windows native SDK account gate (with Java 21 on PATH and an Android emulator running): `npx firebase emulators:exec --project demo-nook --only auth,firestore,storage "powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-native-firebase.ps1"`. It runs the opt-in Android Firebase test and restores the previous Wi-Fi/mobile-data state. Debug-only network policy permits cleartext for 10.0.2.2, localhost and 127.0.0.1, without subdomains; release policy is unchanged. The test passes registration/guest upload, cross-client record updates, permanent deletion, byte-exact Storage transfer and owner isolation. It invokes native SDK adapters directly; configured bootstrap/account UI have a separate passing gate, and product SyncEngine original transfer and deletion cleanup pass in the SDK gate. Ordinary offline instrumentation skips this backend test.

For development, run `npm run test:rules` (requires Java 21 or newer). The suite starts Auth, Firestore and Storage emulators, applies the actual rules and runs ownership, malformed-write, version-order, tombstone and attachment tests.

For production, create a dedicated Nook Firebase project, register web and Android apps, enable desired Authentication providers, create Firestore and Storage, and deploy the rules/indexes with that explicit project ID. Android uses its own nook-firebase.json public configuration; web uses its own public Firebase configuration. None have been provisioned in this workspace.

The normalized path is users/{uid}/records/{id}; kind identifies the conceptual table. Original attachment files live at users/{uid}/attachments/{attachmentId}/original. Original filenames remain in metadata/export; imported filenames and storagePath never select cloud paths. The device database remains the runtime source of truth. Firebase uses server transactions for conflict comparison; it is not part of local capture commits.

Both product sync engines reconcile files after receiving cloud metadata. Persisted attachment records and local originals remain the retry ledger after metadata acknowledgement, so upload/download failures survive process death and do not block unrelated records/files. Files committed after a sync snapshot wait for their metadata to reach the server. Downloads verify the declared size and SHA-256 custom metadata before an atomic local write; a concurrent tombstone or newer record rejects the late bytes. Uploads verify existing immutable original identity, and active upload tasks are cancelled when sync stops. Retained tombstones retry idempotent cloud cleanup. Originals are limited to 50 MiB; transfer currently buffers one original in memory and scans attachments each sync. Transfer status/counts, large-account efficiency and large-file behavior still need final acceptance.

Storage rules require authenticated ownership, a live attachment and live parent in Firestore, matching declared size and a 64-character SHA-256 field. A different checksum cannot overwrite an existing original. Deletes remain owner-authorized after tombstoning; uploads/reads fail once the attachment or parent is deleted. Production rule deployment must enable the Storage-to-Firestore permission described in [Firebase rule conditions](https://firebase.google.com/docs/storage/security/rules-conditions). No production deployment has occurred.

Configure the dedicated bucket's CORS policy for direct authenticated browser downloads. Copy firebase/storage.cors.example.json, replace YOUR-NOOK-WEB-HOST with the deployed origin, and apply it to the explicit Nook bucket with `gsutil cors set <configured-file> gs://<nook-bucket>`. Keep the public Storage bucket configuration on both platforms. Download requests use the SDK with Auth, without persisting public download-token URLs. References: [Web direct download and CORS](https://firebase.google.com/docs/storage/web/download-files), [Android bounded download](https://firebase.google.com/docs/storage/android/download-files), [Android upload cancellation](https://firebase.google.com/docs/storage/android/upload-files).

The web `AuthSession` and `firebaseAuthPort` connect Firebase Authentication to the account-session domain controller. Restoring an authenticated session selects its namespace without silently importing local guest records. Explicit guest sign-in or registration performs the existing atomic merge. The Firebase pre-change callback stops the active sync worker before credentials change; failed sign-out reconciles and resumes the same account. Passwords remain in transient method arguments and Firebase Auth, outside records, exports and outboxes. The emulator suite verifies registration, initial upload, sign-out and switching between two distinct account namespaces. Application bootstrap, account settings and automatic scheduling are connected on both platforms.

Authentication lifecycle reference: [Firebase Auth state hooks](https://firebase.google.com/docs/reference/js/auth#beforeauthstatechanged).

Native `AuthSession` and `FirebaseAuthPort` implement the corresponding email/password lifecycle. Auth operations stop the active sync worker before changing credentials, serialize with observer reconciliation, preserve guest/account namespaces and reconcile credentials even when the initiating coroutine is cancelled. Listener cleanup prevents disposed sessions from restarting workers. This lifecycle has Room-backed domain coverage and real native SDK/UI emulator coverage, and is connected to Android bootstrap, persisted preferences and settings controls. Native API reference: [Firebase Android password authentication](https://firebase.google.com/docs/auth/android/password-auth).

Web settings now expose Google sign-in, email sign-in/registration, manual sync and disconnect. Email registration, guest capture upload, disconnect isolation, sign-in and authenticated reload pass in the actual configured browser against Auth/Firestore emulators. Google uses Firebase's popup provider adapter; production OAuth is not yet exercised and requires Google provider enablement and authorized domains in the dedicated project. Reference: [Firebase Google sign-in](https://firebase.google.com/docs/auth/web/google-signin).

Windows browser account gate (with Java 21 on PATH): `npx firebase emulators:exec --project demo-nook --only auth,firestore,storage "powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-web-auth.ps1"`. The script builds with public demo configuration, runs the two dedicated account/original-file flows, then restores the ordinary build. Execution policy applies only to that helper process. The default `npm run test:e2e` skips the two configured account/original-file flows and runs the fourteen local/offline flows.

Web bootstrap reads the public `VITE_FIREBASE_*` variables documented in `apps/web/.env.example`. Leave them unset for local-only mode. Partial configuration is rejected; `demo-*` project IDs require explicit emulator routing. The Firebase modules load dynamically only for configured startup. A restored identity selects its account-scoped repository before rendering; React context captures that repository in each editor, and changing accounts remounts the application to discard prior navigation, dialogs and unsaved drafts. The component regression test uses distinct namespaces and confirms prior records remain isolated and drafts remain unsaved. Automatic background sync observes committed outbox changes, reconnect events and a 30-second retry/pull timer. Retry metadata changes do not trigger a busy retry loop. Stopping a worker fences pending SDK promises, returns without waiting for offline retries, and rejects late local results; an already submitted remote request may finish only against its original account path.

References: [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions), [Authentication emulator](https://firebase.google.com/docs/emulator-suite/connect_auth), [Firestore emulator](https://firebase.google.com/docs/emulator-suite/connect_firestore).
